# Native Custom Fields (NCF) — Project Rules

WordPress plugin that builds custom fields (post meta, term meta, user meta, options pages) using native Gutenberg/`@wordpress/components` UI. Current version: **1.4.0** (see `native-custom-fields.php`, `package.json`, `includes/Common/Constants.php::VERSION`).

- PHP >= 7.4, WordPress >= 7.0, license GPL-2.0-or-later
- Namespace `NativeCustomFields\` is PSR-4 mapped to `includes/`
- DI: PHP-DI with autowiring (`Common/DI.php`). Get instances via `DI::container()->get( Foo::class )`.
- The plugin can also be booted externally/Composer via `App::boot( $config )`. Don't break this path.

## Architecture

```

├── uninstall.php

├── docs/                           # User/developer docs (DocsPress). abilities/, components/, developer-guides/, user-guides/
├── languages/                      # .pot/.po/.mo

├── src/                            # React source (alias: @nativecustomfields)
│   ├── admin/                      # Admin builder app (pages/: dashboard, create-post-meta, create-term-meta, create-user-meta, create-options; styles/)
│   ├── client/                     # Runtime field rendering on edit screens / options pages
│   ├── common/                     # helper.js, optionsHelper.js, shared assets
│   ├── components/                 # One folder per reusable field component (Repeater, Group, MediaLibrary, DataForm, ...) + index.js barrel

    ├── Common/                     # Constants.php, DI.php, Helper.php (sanitization & utilities)
    ├── Models/                     # DTOs: Common/, Options/, PostMeta/, TermMeta/, UserMeta/ (*Model, *ResponseModel)
```

### Layer responsibilities

- **Services** → business logic, registration of post types / taxonomies / meta / meta boxes / options pages, applying extension filters.
- **Repositories** → persistence only. No business logic, no hooks to the outside.
- **Controllers** (Presentation) → wire WordPress hooks (`add_action` in constructor), register REST routes, validate request + permission, delegate to a Service, return `ResponseModel`/`WP_REST_Response`. **No business logic in controllers.**
- **Models** → plain DTOs for requests/responses and config shapes.
- **Common** → constants, DI, stateless helpers (`Helper::` sanitizers, nonce checks).
- **Interfaces** → new Service capabilities for meta types should extend/implement the existing interfaces.

Flow: `native-custom-fields.php` → `App::run()` → services (`plugins_loaded`) → `ControllerInit` (`init`, 5) → controllers register hooks/REST → services → repositories.

New Service → add to `App::$services`. New Controller → add to `ControllerInit::$controllers`. Both lists are filterable; keep them filterable.

## Naming conventions

| Thing | Convention | Example |
|---|---|---|
| PHP classes / namespaces | `PascalCase` | `PostMetaService` |
| PHP methods / functions in classes | `camelCase` | `registerPostTypes()` |
| PHP variables | `snake_case` (some existing code uses camelCase for properties — match the file) | `$post_types`, `$this->postMetaService` |
| Constants | `UPPER_SNAKE` | `NATIVE_CUSTOM_FIELDS_PATH` |
| Global functions (only in main file) | `camelCase`, `nativeCustomFields` prefix, wrapped in `function_exists` | `nativeCustomFieldsInitActivation` |
| Hooks, options, REST/ajax actions, nonces | `native_custom_fields_` prefix (snake_case) | `native_custom_fields_post_types` |
| Slugs, text domain, folders, files (non-class), ability namespace | `native-custom-fields` | `native-custom-fields/create-post-type` |
| REST namespace | `native-custom-fields/v1` | |
| JS components | `PascalCase` files + folder | `src/components/Repeater/` |
| JS helpers/vars/functions | `camelCase` | `getDefaultValue` |
| JS import alias | `@nativecustomfields/...` | `@nativecustomfields/common/helper.js` |

## PHP rules

- Every PHP file: `<?php`, docblock, `namespace`, `use` imports, then `defined( 'ABSPATH' ) || exit;`. Import every used class with `use` (including `WP_Post`, `WP_Error`, `Exception`, etc.) — no inline FQCNs.
- Follow WordPress Coding Standards (`phpcs.xml`: WordPress-Core + WordPress-Docs; file-name sniff excluded for PSR-4 class files). Run `npm run lint:php` / `composer`-installed phpcs on touched files.
- Type hints and return types on all new methods (`strict_types` is declared in the main plugin file; PHP 7.4 compatible — **no** PHP 8 features: no `match`, no union types, no constructor promotion, no `str_contains`, no named args, no nullsafe `?->`).
- Dependencies are constructor-injected (autowired). Don't `new` services/repositories manually; don't use globals/singletons other than `DI`.
- Class-level docblock must contain `@package NativeCustomFields`, `@subpackage <Layer>`, `@since x.x.x`.
- **Every new class, method, function, property, constant and hook gets `@since`.** See below.

## `@since` rule (IMPORTANT)

Whenever a **new** class, method, function, property, constant, hook (`apply_filters` / `do_action`), REST route or ability is created, document it with `@since x.x.x` — **literally `x.x.x`**. The real version number is substituted at release time. Do NOT guess/insert the current version, and do NOT change the `@since` of existing code.

```php
/**
 * Short description of what it does
 *
 * @param string $post_type Post type slug
 * @return array
 * @since x.x.x
 */
public function getPostTypeFields( string $post_type ): array
```

Class docblock:

```php
/**
 * Describe the class
 *
 * @package NativeCustomFields
 * @subpackage Services
 * @since x.x.x
 */
```

Same applies to JS: new components/functions get `@version x.x.x` (existing JS docblocks use `@version`; PHP uses `@since`). Also when a new hook is added, document it in `docs/developer-guides/6_hooks.md`.

## Security (always)

- Sanitize first, escape later, always validate. Use `Helper::` sanitizers for field values (they pass through the `ncf_sanitize_field_value` filter); `sanitize_*` for other inputs; `esc_html/esc_attr/esc_url/wp_kses_post` on output.
- REST routes: always define `permission_callback` (capability check via `current_user_can()`, never `__return_true` for write routes). Admin form/AJAX actions: nonce (`wp_verify_nonce` / `check_ajax_referer` via `Helper`) + capability check.
- Use `$wpdb->prepare()` for any SQL; prefer WP APIs and avoid raw queries.
- Translatable strings: `__()`, `_e()`, `esc_html__()` etc. with text domain `native-custom-fields` (literal string, never a variable). JS: `@wordpress/i18n` with the same domain.
- Performance: minimize queries, cache with transients/object cache when appropriate, enqueue assets only on the screens that need them (see `AdminController` / `ClientController`).

## Extensibility (hooks)

- Existing hooks use the `native_custom_fields_` prefix (exception: `ncf_sanitize_field_value`, kept for BC). New hooks must use `native_custom_fields_`.
- Don't remove or change signatures of existing hooks (public API; documented in `docs/developer-guides/6_hooks.md`).
- Configuration is stored in options (via Repositories); runtime values in post/term/user meta and options. See `docs/developer-guides/` before changing storage shape — it is a BC surface (and import/export depends on it).

## Abilities (WordPress Abilities API)

- Live in `includes/Services/Abilities/*AbilitiesService.php`, loaded through `Presentation/Admin/Controllers/AbilityController.php`. Reuse `AbilityFieldAdapterTrait` for field schemas.
- Ability names: `native-custom-fields/<verb>-<noun>`; category: `native-custom-fields`.
- If an ability needs no input, do **not** pass an empty `input_schema` (omit it) — providers call zero-arg tools with no arguments.
- Always provide `permission_callback` with a capability check and an `execute_callback` that delegates to existing Services (no duplicated logic).
- Document each ability in `docs/abilities/` and keep `docs/abilities/field-schema.md` consistent.

## JavaScript / React rules

- Source in `src/`, built to `build/` by `@wordpress/scripts`. Never hand-edit `build/`.
- Use `@wordpress/components`, `@wordpress/element`, `@wordpress/data`, `@wordpress/api-fetch`, `@wordpress/i18n`, `@wordpress/icons`. Avoid adding UI libraries; drag-and-drop uses `@dnd-kit`.
- New field type checklist:
  1. Component in `src/components/<Name>/` and export from `src/components/index.js`
  2. Builder config `src/configurations/fields/fieldCustomInfo<Name>.js` (+ register in `fieldCustomInfoList.js` / `field-configurations.js`)
  3. Render wiring in `src/render/RenderSingleField.js`
  4. PHP: field type palette (`FieldService`), sanitization in `Helper`, ability schema if exposed
  5. Docs in `docs/components/<name>Control.md`
- Styles: SCSS in `src/admin/styles` / `src/client`; lint with `npm run lint:css`, `npm run lint:js`.
- Use the `@nativecustomfields` alias for imports, JSDoc on components with `@version x.x.x` for new ones.

## Dev workflow

1. `composer install` (or `composer update`)
2. `npm i`
3. `npm start` (watch) / `npm run build` (production)
4. Lint: `npm run lint:php`, `npm run lint:js`, `npm run lint:css`
5. Releasing: bump version in `native-custom-fields.php`, `package.json`, `includes/Common/Constants.php`, `readme.txt` (Stable tag + changelog), then replace `x.x.x` in `@since` tags with the release version. `package-lock.json` also carries the version (top-level `version` and `packages[""].version`); update those two lines only, not the dependency versions.

## Git workflow

The plugin is consumed through Composer, which resolves versions from Git tags. **Every release needs a new tag; never reuse, move or delete a published tag.**

- Work on `main`. The remote is `origin` (GitHub `Arkenon/native-custom-fields`).
- Commit and push only when asked.
- Commit messages follow Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:` ...). A release commit puts the version in the subject, e.g. `feat: add read-only abilities and fix options page builder state (1.4.1)`.
- Release flow:
  1. Bump the version everywhere listed under "Dev workflow" step 5, add the changelog entry to `readme.txt`, and replace `x.x.x` in `@since` tags with the release version.
  2. `git status`, then stage the intended files explicitly. Leave out local-only or unrelated files; ask when unsure, because the repo is public.
  3. Commit.
  4. Create the tag with a `v` prefix and the plugin version: `git tag v1.4.1`. Tags are lightweight, like the existing ones (`v1.4.0`, `v1.3.9`, ...).
  5. Push the branch, then the tag: `git push origin main` and `git push origin v1.4.1`.
- Commits that are not a release (docs, tooling) do not get a tag.

## Do / Don't

- Do respect the layer boundaries and existing folder structure; match surrounding code style (the repo mixes tabs/spaces — follow the file you edit).
- Do keep backward compatibility for stored configuration, hooks and REST routes.
- Do update `docs/` when behavior, hooks, abilities or components change.
- Don't modify `vendor/`, `node_modules/`, `build/`.
- Don't add business logic to controllers or repositories.
- Don't use PHP > 7.4 syntax.
- Don't modify third-party plugin code; solve everything inside this plugin.
